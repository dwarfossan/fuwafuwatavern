# 四層分離完成驗收（2026-10-01）

已完成地板、標示、物件＋角色、介面的獨立更新，以及戰鬥更新呼叫路由與驗收。提交在 `layers`；不合併 `dev`／`main`，等大爺實機確認。

## 完成範圍

| 層 | 更新入口 | 更新時機 |
|---|---|---|
| 地板 | `updateBoardFloor()` | 地圖寬高、道路、高度資料變更；新戰鬥初次建立 |
| 標示 | `updateBoardMarks()` | 移動範圍、技能／物品瞄準、選擇條件變更 |
| 物件＋角色 | `updateBoardScene()` | 位置、面向、動作、血量、狀態、掉落、觀察符號、台詞、攻擊演出變更 |
| 介面 | `updateBattleUI()` | 回合、指令、资源、骰子、紀錄、角色卡、教學、系統選單變更 |

`refreshBattle()` 依資料依賴判斷哪些層要更新，沒有產生 HTML 再比對、沒有 debounce、沒有移動補償、沒有逐個棋子修補。每次更新完整的指定層。地板與標示使用 SVG 原生 paint server；台地在物件層引用地板幾何，維持原本遮擋排序。三個 SVG 群組共用同一個鏡頭。

當前棋子腳下的光移到物件＋角色層，避免走一步就重算整張移動範圍。一般走路每一步只重畫物件＋角色；開始／結束移動和途中觸發藉機攻擊、拾取、揭露等事件仍更新有變動的介面。介面是一個邏輯層，DOM 分布於上方與戰場覆蓋區，沒有改原本版面。

`flow.js`、`engine.js` 的修改以原版逐字比對，只有 `render();` 換成 `refreshBattle();`，規則、流程、數值未改。共用詳情卡在戰鬥頁走分層更新，在其他頁仍走原本 render。持續存在的按鈕以 WeakMap 記錄已綁定的事件，避免重複綁定；新介面節點各自綁定。重新挑戰建立新戰鬥與新圖層，離開戰鬥仍切頁。

## CPU 4× 測量

Chromium 153、Playwright、390×844，30 次樣本。數字測量 JavaScript／DOM 更新耗時，不包括完整合成與螢幕刷新，也不是實機 FPS。詳見 `results.json`、`motion-results.json` 原始樣本。不同批次會受 GC 與環境負載影響。

| 操作 | 原版中位數／p95 | 四層版中位數／p95 |
|---|---:|---:|
| 狀態未變的重複 render | 104.7／157.2 ms | 5.7／10.8 ms |
| 真正走路一步（呼叫 walk） | 90.2／206.0 ms | 52.3／85.1 ms |
| 只更新標示 | 無獨立入口 | 4.8／11.2 ms |

一般步行中位數約減少 42%；無狀態變化的 render 約減少 95%，後者是避免不必要更新，不能當成步行效能。標示場景驗收 DOM 數原版 1,711／四層版 2,186；本次減少重畫，沒有宣稱節點變少。

## 實機確認與保留問題

請在手機確認移動／取消、攻擊與骰子、狀態卡／背包、拖曳／雙指縮放、重開戰鬥。自動化是真實瀏覽器觸控事件，尚未驗證大爺手機的實際瀏覽器。
